# Kafka и RabbitMQ

## Подготовка

Нужны Docker с Compose v2 и Bash. На macOS запустите Docker Desktop. На Windows используйте WSL2 с включённой интеграцией Docker Desktop. Выделите Docker 4 CPU и 6–8 ГБ RAM. Для первой загрузки образов нужен интернет.

Откройте терминал в папке с `lab.sh` и `compose.yaml`. Все команды ниже выполняются из неё.

```bash
docker version
docker compose version
chmod +x lab.sh
./lab.sh prepare
```

`prepare` скачивает образы, собирает клиент и запускает брокеры. Дождитесь `rabbit.ready` и `kafka.ready` с брокерами `[1, 2, 3]`.

Для повторного запуска подготовленного окружения выполните

```bash
./lab.sh up
```

Проверить подключение без перезапуска контейнеров можно командой `./lab.sh check`.

## RabbitMQ

Запускайте команды по одной и сравнивайте результат с таблицей.

```bash
./lab.sh rabbit routing
./lab.sh rabbit redelivery
./lab.sh rabbit idempotency
./lab.sh rabbit dlq
```

| Опыт | Результат |
|---|---|
| `routing` | Два воркера делят 6 событий, аудит получает отдельные 6 копий. Публикация без маршрута возвращается издателю |
| `redelivery` | После записи в БД воркер завершается до ack. То же событие приходит с `redelivered=true`, счётчик увеличивается до 2 |
| `idempotency` | Повторная доставка происходит, но `applied=false` и счётчик остаётся равен 1 |
| `dlq` | Некорректное изображение попадает в очередь ошибок с `reason=rejected`. Счётчик остаётся равен 0 |

В `routing` поле `ready` показывает сообщения, ожидающие доставки. Уже выданные, но не подтверждённые сообщения в него не входят. Распределение событий между воркерами может меняться.

Дополнительный опыт с ограничением неподтверждённых доставок

```bash
./lab.sh rabbit prefetch
```

При `prefetch=1` потребитель получает одно сообщение и ждёт ack. При `prefetch=4` — четыре. Эти опыты используют classic queues на одном узле. В `routing` и `prefetch` сообщения поступают через подписку, в остальных опытах клиент запрашивает их через `basic_get`. На `basic_get` лимит prefetch не действует.

## Kafka

### Группы потребителей и offsets

```bash
./lab.sh kafka groups
./lab.sh kafka replay
./lab.sh kafka commit
```

| Опыт | Результат |
|---|---|
| `groups` | У топика 2 раздела, в группе 3 участника. Один остаётся без назначения. Группы analytics и audit независимо читают по 12 событий |
| `replay` | После `seek(0)` клиент повторно читает записи с offsets 0, 1, 2. Сохранённый offset группы остаётся равен 3 |
| `commit` | Сбой после раннего commit приводит к пропуску работы. Сбой после обработки, но до commit, приводит к повторной обработке и счётчику 2 |

В `commit` дождитесь завершения обоих случаев. После падения воркера новый клиент вступает в ту же группу; это занимает некоторое время.

### Отказ брокера и репликация

```bash
./lab.sh kafka baseline
./lab.sh kafka failover
./lab.sh kafka min-isr
```

| Опыт | Результат |
|---|---|
| `baseline` | Три реплики входят в ISR. Запись подтверждена с `acks=all` и `minISR=2` |
| `failover` | Текущий лидер остановлен. Новый лидер принимает запись при ISR из двух реплик. Клиент читает записи до и после отказа |
| `min-isr` | При ISR из двух реплик и `minISR=3` публикация завершается ошибкой `NOT_ENOUGH_REPLICAS` или `NOT_ENOUGH_REPLICAS_AFTER_APPEND`. После возврата `minISR=2` публикация проходит |

`failover` и `min-isr` создают отдельный топик для каждого запуска и в конце восстанавливают остановленный узел. Запускайте их последовательно. Если опыт был прерван и узел не восстановился, выполните `./lab.sh up`.

## Паузы и общий прогон

Между действиями клиента добавлены паузы по 1,5 секунды. Чтобы увеличить паузу, задайте `LAB_DEMO_DELAY` от 0 до 5 секунд.

```bash
LAB_DEMO_DELAY=3 ./lab.sh rabbit routing
```

Для проверки всех десяти основных опытов без этих пауз выполните

```bash
./lab.sh all
```

Каждый успешный опыт отмечается строкой `OK`. При ошибке скрипт выводит журнал и останавливается.

## Результаты обработки

Миниатюры и базы SQLite хранятся в Docker volume. Скопировать их в локальную папку `data/` можно командой

```bash
./lab.sh export
```

Имя миниатюры текущего опыта указано в поле `preview`. В `data/` сохраняются и результаты предыдущих запусков.

[Интерфейс RabbitMQ](http://127.0.0.1:15682) доступен с логином `student` и паролем `student-local`. Выберите vhost `s6`. После опытов очереди могут быть пустыми — сообщения уже прочитаны и подтверждены. В опыте `dlq` клиент также извлекает сообщение из очереди ошибок.

## Изменение кода

| Файл | Содержимое |
|---|---|
| `app/rabbit_demo.py` | Маршрутизация, подтверждения, повторная доставка и DLQ |
| `app/kafka_demo.py` | Группы потребителей, offsets, смена лидера и minISR |
| `app/common.py` | Обработка изображения и транзакции SQLite |

| `compose.yaml` | Конфигурация контейнеров и сети |

После изменения Python-кода пересоберите клиент и повторите нужный опыт.

```bash
docker compose build lab
```

## Если запуск не удался

| Проблема | Что сделать |
|---|---|
| Docker недоступен | Запустите Docker Desktop. В выводе `docker version` должна появиться часть Server |
| Образы не скачиваются | Проверьте доступ к Docker Hub и повторите `./lab.sh prepare` |
| Брокеры не готовы | Проверьте `docker compose ps` и `docker compose logs --tail=100 kafka1 kafka2 kafka3 rabbit`, доступную память и место на диске |
| Порт 15682 занят | Освободите порт или измените внешний порт в `compose.yaml` и адрес интерфейса RabbitMQ |
| После прерванного опыта Kafka недоступна | Выполните `./lab.sh up`, затем `./lab.sh check` |
| Изменения Python-кода не применились | Выполните `docker compose build lab` |

## Остановка

```bash
./lab.sh stop
```

Данные в volumes сохраняются. Для полного сброса данных этого проекта выполните `docker compose down -v`. Экспортированные файлы в `data/` останутся на компьютере.

## Самостоятельная работа

1. Запустите `prefetch`. Объясните, почему до ack доставляется только заданное число сообщений и как это связано с числом потоков воркера.
2. По выводу `groups` объясните назначения разделов. Что изменится, если запустить четырёх участников с теми же двумя разделами?
3. Добавьте защиту от повторной обработки в опыт `commit`. Передайте `dedupe=True` вызовам `process_image` в функциях `crash_worker` и `commit`. Для позднего commit измените ожидаемый счётчик с 2 на 1. Пересоберите клиент и проверьте оба случая. Ранний commit по-прежнему должен давать 0.
4. Нарисуйте outbox для результата обработки изображения. Укажите границу транзакции и место, где отправка события может повториться.

Для каждого опыта запишите прогноз, команду, результат и объяснение.
